## Expected behavior

An unpaired browser that can request pairing should show **Request access** instead of **Offline**.
Selecting it should open `/pair?request` in the same WebView.
A real connection failure should remain distinguishable and shouldn't offer pairing as its remedy.

## Actual behavior

A fresh Chromium profile shows `Disconnected from <dashboard-host>. Retrying…` and an **Offline** connection chip.
It doesn't offer **Request access**.

This is a dead end in an iOS home-screen WebView because it has no address bar.
In my case, Firefox was already paired, but the home-screen WebView wasn't.
Deleting and recreating the bookmark didn't help.

Opening `/pair?request` directly in a second fresh Chromium profile shows the pairing page and its **Request access** button.
The pairing page works, but the dashboard doesn't provide a way to reach it.

## Reproduction

1. Run PI Dashboard 0.11.0 without an OAuth provider and with this configuration:

   ```json
   {
     "port": 18849,
     "bindHost": "0.0.0.0",
     "autoShutdown": false,
     "tunnel": {
       "enabled": false
     },
     "network": {
       "trustMode": "pair",
       "trustModeOrigin": "operator"
     },
     "pairing": {
       "acceptLanRequests": true
     }
   }
   ```

2. Open `http://<dashboard-host>:18849/` from a fresh remote browser profile with no paired-device cookie.
3. Observe that the dashboard shows **Offline** without a **Request access** action.
4. Open `http://<dashboard-host>:18849/pair?request` in another fresh profile.
5. Observe that the pairing page shows **Request access**.

<summary>Source analysis and environment</summary>

`useNetworkDenied` probes the public `/api/health` endpoint.
It recognizes only a `403 network_not_allowed` response or a `200` response containing `localProof: "required"`.

https://github.com/BlackBeltTechnology/pi-agent-dashboard/blob/7d07c461aac948c49e58d9a9393a21aaa1c05ab4/packages/client/src/hooks/useNetworkDenied.ts#L33-L49

The network guard exempts `/api/health`, so an unpaired remote caller receives `200` instead of the denial response that the hook expects.

https://github.com/BlackBeltTechnology/pi-agent-dashboard/blob/7d07c461aac948c49e58d9a9393a21aaa1c05ab4/packages/server/src/auth/localhost-guard.ts#L519-L532

The health response reports `localProof` only for a loopback caller.
It doesn't report the remote caller's network denial or whether **Request access** is available.

https://github.com/BlackBeltTechnology/pi-agent-dashboard/blob/7d07c461aac948c49e58d9a9393a21aaa1c05ab4/packages/server/src/routes/system-routes.ts#L1252-L1259

The current pair-mode browser test requires OAuth and accepts either **Request access** or the OAuth sign-in screen.
It doesn't cover the authentication-disabled configuration above.

https://github.com/BlackBeltTechnology/pi-agent-dashboard/blob/7d07c461aac948c49e58d9a9393a21aaa1c05ab4/tests/e2e/trust-mode-pair.spec.ts#L39-L68

One possible fix is for the public status response to include the caller-specific admission result and pairing remedy from the same network decision.
