# Work selection

Choose a bounded next action within the current authorized task or goal.
Use this procedure for implementation, research, writing, planning, and review; an active goal is not required.
Do not wait until the work stalls or decide that the current approach is wrong before reassessing it.

This skill does not activate autonomous execution or authorize implementation of a plan, repairs during a review, publication, or resuming an inactive goal.
[Autonomous-work](../autonomous-work/SKILL.md) owns unattended-run authority, persistence, acceptance order, and stopping; goal tools own status changes and budgets.
Use [opportunity-scan](../opportunity-scan/SKILL.md) for project-wide discovery when no task is selected, not to expand the current task.

## Recover the outcome and governing constraints

Read the request, governing references, current artifacts, and outcome evidence.
Identify the permitted activity, current unmet acceptance condition, and missing evidence or demonstrated dependency the proposed work addresses.
Use the activity's actual criteria: sources and reasoning for research, the brief for writing, feasibility for planning, inspection evidence for review, and consumer behavior for implementation.
Preserve required milestone order and integration obligations; another unmet item alone does not justify abandoning them.
Keep scoped blockers and other independent authorized work visible.

Separate user instructions and other governing requirements from agent-authored assumptions, restrictions, and intermediate acceptance criteria.
Cite the source of consequential constraints; never attribute an agent-imposed restriction to the user.
Approval to execute a plan does not by itself make every plan detail a governing requirement.
Ask before changing governing scope, required acceptance, preservation obligations, permissions, or user-required or explicitly approved design choices.
Within existing authorization, revise or retire agent-authored restrictions, milestones, and intermediate criteria when a better approach meets the same governing requirements.
Record supersession in existing permitted task state and update affected dependencies; do not retain an abandoned approach as a prerequisite or claim its unmet criteria passed.
Record permitted defaults as assumptions; leave missing judgments unresolved.

## Check the proposed supporting work

Before adding another substantive prerequisite, workaround, or diagnostic round, name the unmet dependency, the acceptance check it prevents, and the supporting evidence.
Compare the smallest existing-tool alternative before adding instrumentation, changing a diagnostic question, or delegating prerequisite work.
Make this comparison even when the last probe produced useful partial evidence or earlier tasks succeeded.
Preserve the outcome and governing constraints, not every agent-selected implementation choice.
A chain of different successful supporting tasks can still fail to advance the requested outcome; reconsider approach-imposed restrictions before treating them as prerequisites.

Repair obvious mechanical failures directly when they need no new mechanism or change of question.
An unrelated bug is not a prerequisite; do not repeatedly review an unchanged boundary or add defenses for hypothetical failures.
Before a diagnostic follow-up, identify which possible finding would change the next action.
Do not produce another assessment without a decision it can change.
Use [creative-inquiry](../creative-inquiry/SKILL.md) when the framing remains uncertain and [design-deliberation](../design-deliberation/SKILL.md) for a genuine software-design fork, not an improvised experiment restriction.

## Scout before extending the approach

At the continuation trigger, use an available compatible fresh-context scout template and follow its advertised caller contract.
Consult [delegation](../delegation/SKILL.md) for assignment, effects, coordination, waiting, and integration; scouting grants no additional effects.
Supply evidence entrypoints for the main user activity as well as current work, so the current approach does not define the search space.
Preserve the latest relevant user correction and its provenance; quote it only when the exact text is available.
Do not supply a preferred task or a parent-written assessment in place of independent evidence inspection.
Without a compatible template, inspect an existing example of the main activity and its outcome evidence yourself.
Keep that assessment read-only; report unavailable evidence and do not claim independence.

Look beyond the current subsystem or line of inquiry for missing core capabilities, including incomplete use of existing machinery, without conducting an exhaustive project audit.
Another investigation is not the required outcome.
Do not scout after every tool call or repeat an unchanged search without new evidence.

## Select and act

Compare the recommendation with continuing current work and the strongest credible competing action.
Include user benefit and its evidenced or estimated scale, plus work through delivery, verification, and coordination.
A correct finding, novelty, coverage total, or completed batch does not establish user-facing quality or justify priority alone.
Do not turn missing evidence into a claimed failure or assume investigation will justify follow-up work.
If uncertain benefit or cost determines the choice, identify the smallest check that distinguishes the competing actions.
Decide when evidence supports a recommendation or identifies a concrete blocker; impose no fixed lookup or time limit.

The parent retains task-selection authority.
Select a bounded authorized action and explain the decisive comparison; do not require a narrated checklist for routine execution.
No better alternative found is a successful result; continue when it wins and name missing context rather than inventing work.
A scout report alone is not progress.
When human input is necessary, identify the exact unresolved decision and continue independent authorized work where possible.
Reassessment neither narrows the user's objective nor changes inactive-goal controls.

## Implementation-specific continuation checks

For end-to-end implementation, two consecutive completed subtasks without a new consumer-visible result also trigger reassessment before more prerequisite or capability work.
Attempt the nearest intended-consumer check; if it cannot run, identify the exact missing dependency and compare repair with the smallest authorized alternative.
Explicit feasibility or component milestones retain their own acceptance conditions.
Connect each handoff to the intended consumer or remove the temporary path before extending it with another fixture-only capability.
If a repair displaces integration, retain integration as the next action for that acceptance condition.

[Design-for-change](../design-for-change/SKILL.md) owns test-strategy choices; [double-check](../double-check/SKILL.md) owns completion audits when its scope applies.
These implementation checks do not impose software-consumer evidence on research, writing, planning, or review.
