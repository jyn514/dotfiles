# Issue reporting

Produce a maintainer-ready title and issue body. Use the project and bug from the
conversation; ask for the target repository only when it cannot be identified.
Assume jyn is reporting to another maintainer. Transfer the evidence they need to
investigate without relying on shared context. For a feature request, use the
project's feature template and describe the user workflow, limitation, and existing
workaround rather than forcing it into a bug report.

## Gather the authoritative inputs

1. Read the target project's current issue template and contribution instructions
   before drafting. For remote source, shallow-clone the repository into a
   temporary directory. Use the applicable bug template, retaining its headings,
   order, and required fields; omit template comments and metadata from the body.
   If no template is available, tell the user and use affected version,
   description, reproduction steps, expected behavior, and output.
2. Incorporate the user's latest corrections and reported experiments. Separate
   user-observed reproduction, agent-observed reproduction, and source inspection.
   A matching source defect does not prove a runtime reproduction. Do not invent
   commands, full logs, environment details, or a successful test.
   Capture relevant local patches, forks, nonstandard configuration, and previous
   attempts with their results. Include a working control when it narrows the
   failure: for example, one picker order fails while the reverse order works.
3. Record the installed version and relevant runtime dependencies. When upstream
   requests testing the development version, inspect that requirement and report
   whether it was met. If testing needs a different build, prefer an isolated
   standalone directory over replacing the installed program. Follow
   `dependency-review` for a requested build or update; do not silently expand
   drafting into installation.
4. Inspect the relevant source in context. Resolve the full commit hash for the
   inspected revision and use GitHub permalinks with that hash and precise line
   anchors. Never use branch names or abbreviated hashes in code links.

## Write the report

- Use complete sentences and ordinary issue prose, even when conversation uses
  IRC style. Be concise without reducing the report to fragments.
- Start the body with an accurate authorship disclosure. For a generated draft:
  `🤖 this issue description was generated by an LLM 🤖`. If jyn edited the text,
  use: `🤖 this issue description was generated by an LLM, with small edits by jyn 🤖`.
  Do not claim human edits that have not occurred.
- State the visible failure and its practical consequence, then explain the cause
  if established. A report need not diagnose the bug; label hypotheses explicitly
  and keep the observed behavior useful even if the diagnosis is wrong. Put each
  bare GitHub permalink on its own line immediately after the claim it supports.
- Include exact version strings, full development commit hashes, and the tested
  invocation. For standalone builds, include the build and resource paths and any
  environment variables needed to load them; without these, a reproduction may
  silently use the installed catalogs.
- Give numbered reproduction steps with a concrete command and the point where
  the failure appears. Include relevant inputs, configuration, cursor position,
  or keystrokes. Label proposed steps as unverified when necessary, and distinguish
  runnable reproducers from illustrative code with omitted setup or placeholders.
  If the reproduction requires inaccessible infrastructure, state that limit and
  provide the available evidence instead of implying anyone can run it.
- Include a failing input or artifact when it helps investigation, even if not yet
  minimized. State the minimization limit. Use screenshots for visual failures and
  collapsible sections for long supporting logs; keep decisive evidence visible.
- Describe expected behavior separately. Include a small fix suggestion only
  when the evidence supports it; do not turn the report into an implementation plan.
- Preserve observed output verbatim in a fenced block. State when it is only an
  excerpt or came from an older version. Never relabel old output as a new test.

## Check and deliver

Check the final body against the template and latest user evidence. Verify that
each code link identifies the inspected revision and lines, reproduction commands
match the reported test, and required fields are filled or explicitly unknown.
Check template attestations individually; do not mark research, clean-environment,
or latest-version checks as completed without evidence.
Return a copy-ready title and body without process commentary inside the report.
Drafting does not authorize submission; submit only when explicitly requested.
