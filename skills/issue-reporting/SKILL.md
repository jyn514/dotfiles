# Issue reporting

Produce a maintainer-ready title and issue body. Use the project and bug from the
conversation; ask for the target repository only when it cannot be identified.
Assume jyn is reporting to another maintainer. Transfer the evidence they need to
investigate without relying on shared context. For a feature request, use the
project's feature template and describe the user workflow, limitation, and existing
workaround rather than forcing it into a bug report.

## Gather the authoritative inputs

1. Read the target project's current issue template and contribution instructions
   before drafting. For remote source, shallow-clone the repository into a
   temporary directory. Use the applicable bug template, retaining its headings,
   order, and required fields; omit template comments and metadata. If no template
   is available, tell the user. Put the required LLM disclosure before the first
   template heading; then preserve the template's heading order and required
   fields. Lead with the installation or invocation and visible failure; include
   reproduction, expected behavior, and output, then put version details at the end.
2. Incorporate the user's latest corrections and reported experiments. Track
   whether each result came from the user, an agent-run check, or source inspection.
   Write verified checks performed by either jyn or the agent in first person as
   jyn, without adding agent attribution. Do not present proposed or unverified
   steps as completed checks. A matching source defect does not prove a runtime
   reproduction. Do not invent commands, full logs, environment details, or a
   successful test. Capture relevant local patches, forks, nonstandard
   configuration, and previous attempts with their results. Include a working
   control when it narrows the failure: for example, one picker order fails while
   the reverse order works.
3. Record the installed version and relevant runtime dependencies. If the project
   requests testing the development version, check that requirement and report
   whether it was met. If testing needs a different build, prefer an isolated
   standalone directory over replacing the installed program. Follow
   `dependency-review` for a requested build or update; do not silently expand
   drafting into installation.
4. Inspect relevant source when the report makes a source-based claim. For GitHub,
   resolve the inspected revision's full commit hash and use a permalink with
   precise line anchors; never use branch names or abbreviated hashes in code
   links. For other hosts, use an equivalent stable, revision-specific link when
   available. Omit source links when the report makes no source-based claim.

## Write the report

- Use complete sentences and ordinary issue prose, even when conversation uses
  IRC style. Write in first person as jyn, using active voice and direct sentences.
  Choose a title that names the general failure rather than one tool that exposes
  it: "user-local Python" rather than "mise Python"; name mise in the body.
  Include facts that help the maintainer reproduce, diagnose, or fix the failure;
  omit investigation narration and redundant checks when a working control
  already establishes the relevant difference.
- Use active voice throughout authored prose, including delivery commentary.
  Name the actor for actions and checks; avoid impersonal subjects such as
  "a diagnostic check confirms" even though they are grammatically active.
  Prefer "I checked the import" or "the launcher calls Python" to "the import
  was checked" or "Python is called". "I" means jyn, including checks the agent
  actually ran on her behalf. Write the report as she would write it by hand;
  do not add agent attribution to individual checks. Preserve required template
  text, the disclosure, and quoted output verbatim.
- Start the issue body with this disclosure, before the template's first heading:
  `🤖 this issue description was generated by an LLM 🤖`.
  Keep the template's headings, order, and required fields after the disclosure.
  Leave any disclosure of later human edits to jyn.
- State the visible failure and its practical consequence, then explain the cause
  if established. A report need not diagnose the bug; label hypotheses explicitly
  and keep the observed behavior useful even if the diagnosis is wrong. Put each
  bare GitHub permalink on its own line immediately after the claim it supports.
- Include exact version strings, full development commit hashes, and the tested
  invocation. Say "using commit ..." rather than narrating source comparisons.
  For standalone builds, include the build and resource paths and any
  environment variables needed to load them; without these, a reproduction may
  silently use the installed catalogs.
- Give a concrete command and the point where the failure appears; use numbered
  steps when reproduction needs several actions or the template requires them.
  Include relevant inputs, configuration, cursor position,
  or keystrokes. Label proposed steps as unverified when necessary, and distinguish
  runnable reproducers from illustrative code with omitted setup or placeholders.
  If the reproduction requires inaccessible infrastructure, state that limit and
  provide the available evidence instead of implying anyone can run it.
- Include a failing input or artifact when it helps investigation, even if not yet
  minimized. State the minimization limit. Use screenshots for visual failures and
  collapsible sections for long supporting logs; keep decisive evidence visible.
- Describe expected behavior separately. Include a small fix suggestion only
  when the evidence supports it; do not turn the report into an implementation plan.
- Preserve observed output verbatim in a fenced block. State when it is only an
  excerpt or came from an older version. Never relabel old output as a new test.

## Check and deliver

Check the final body against the template and latest user evidence. Verify that
each code link identifies the inspected revision and lines, reproduction commands
match the reported test, and required fields are filled or explicitly unknown.
Check template attestations individually; do not mark research, clean-environment,
or latest-version checks as completed without evidence.
Review each authored sentence for passive voice and hidden actors before
delivery. Rewrite it with the known actor or a direct statement of behavior;
do not invent an actor to satisfy the style rule.
Return a copy-ready title and body. Keep process commentary, remaining checks,
and the issue-creation URL outside the report body. For each check that remains,
give the exact check to run and which sentence or field to replace for each
possible result. Keep unverified claims out of the report; do not turn agent
limitations into first-person claims or claim checks that neither jyn nor an
agent performed. Incorporate her results when she supplies them. If no material
checks remain, say so briefly. After the first draft of each report, provide the
upstream issue-creation URL outside the report body so jyn can submit it.
Drafting does not authorize submission; submit only when explicitly requested.
