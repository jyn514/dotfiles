## Expected behavior

When Pi replaces the owning extension runtime during `/resume`, the new extension instance should be allowed to initialize the Dashboard bridge.

## Actual behavior

The outgoing session unregisters, but the replacement is rejected as subagent re-entry and never registers.
The Pi session keeps running while disappearing from Dashboard.

This differs from #393 and the stale `ctx.cwd` fix in #397.

## Requested behavior

Release bridge ownership when the owning runtime shuts down for session replacement, including `resume`, `new`, and `fork`.
Keep rejecting a different Pi instance when it loads while the current owner remains active, so a subagent cannot take over its parent's bridge.

## Minimal reproduction

From a Dashboard checkout, save this as `repro.ts` in the repository root and run `pnpm exec tsx repro.ts`:

```ts
import {
  isBridgeReentry,
  releaseBridgeOwnerOnShutdown,
} from "./packages/extension/src/terminal-reload.js";

for (const reason of ["reload", "resume"]) {
  const owner = { generation: 1, pi: {} };
  releaseBridgeOwnerOnShutdown(owner, reason);
  console.log(reason, isBridgeReentry(owner, {}));
}
```

Output on Dashboard 0.11.0:

```text
reload false
resume true
```

Both cases replace the owning extension runtime with a fresh `ExtensionAPI`.
`reload` releases bridge ownership, but `resume` leaves the old owner in place, so the replacement is classified as a subagent.

The relevant helper only releases ownership for `reason === "reload"`:

https://github.com/BlackBeltTechnology/pi-agent-dashboard/blob/11b3058123aab9234f0d6af1884c9c5c604403b9/packages/extension/src/terminal-reload.ts#L276-L298

Pi's actual `/resume` path confirms the consequence with the unmodified published packages `@earendil-works/pi-coding-agent@1.5.0` and `@blackbelt-technology/pi-agent-dashboard@0.11.0`:

```text
PI:        session_start reason=startup
Dashboard: session_register outgoing

# switch to another conversation with /resume

Dashboard: session_unregister outgoing
PI:        session_shutdown reason=resume
PI:        session_start reason=resume
Dashboard: [missing] session_register incoming
```

`PI:` lines are extension lifecycle events emitted by Pi.
`Dashboard:` lines are messages observed on the bridge's WebSocket connection.
`outgoing` and `incoming` stand for the two distinct session IDs rather than literal log values.

The initial `session_start` and `session_register` show that the bridge loads and registers normally.
During `/resume`, Dashboard unregisters the outgoing session and Pi shuts down its extension runtime with `reason=resume`.
Pi then starts a fresh extension runtime for the incoming conversation, also with `reason=resume`.
That runtime never sends the expected `session_register incoming`, so the conversation remains active in Pi but absent from Dashboard.

The unregister line appears before the shutdown line because Dashboard's shutdown handler sends the unregister message before the diagnostic handler prints the same lifecycle event; it does not initiate the shutdown.
Opening the same incoming session in a fresh process registers successfully.
The runtime check used Pi's real `switchSession()` API, a temporary HOME, disabled model networking, and a loopback WebSocket recorder; it required no credentials or running Dashboard server.
